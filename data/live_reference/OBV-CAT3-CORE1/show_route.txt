dette er fra Core i zonen CAT3DMZ.. 

Ja — det her er den rigtige CAT3DMZ core (OBV-CAT3-CORE1), og configen er meget værdifuld for modellen.

Vi kan bl.a. se, at core’en har alle CAT3DMZ-zonerne som separate VRF’er med egne RT’er, fx CAT3DMZ-51-TPS-INT-SERVER med RT 65330:35029. Core’en har også det konkrete linknet til TPS INT på Vlan3529, IP 100.73.65.118/30.

Samtidig ser vi den fysiske/L2-forbindelse til firewall-clusteret via Port-channel1, som trunker alle de relevante CAT3DMZ link-VLANs til OBV-CAT3-FW1.

Det betyder, at vores topologimodel kan blive meget stærkere:

OBV-CAT3-FW1
   │
Port-channel1 trunk
   │
OBV-CAT3-CORE1
   ├─ VRF CAT3DMZ-11-COMM
   ├─ VRF CAT3DMZ-46-SW-CITRIX-SVR-ENV
   ├─ VRF CAT3DMZ-51-TPS-INT-SERVER
   └─ ...

Og for eksempel CAT3DMZ-11-COMM har firewall/core-linket på Vlan3311 med core-IP 100.73.34.42/30.

Det interessante er dog: den route vi lige arbejder med — 100.72.36.64/27 — findes på CAT3-firewallen mod CAT2DMZ, ikke i en CAT3DMZ server-VRF på denne core. Så til den konkrete trace-blocker har firewallens show route allerede givet os det afgørende datapunkt.

Jeg ville derfor ikke hente hele routing-tabellen fra core’en nu. Men mens du har adgang, vil jeg meget gerne have to små outputs, fordi de bliver perfekte validationsdata til Network Modernizer:

show ip route vrf CAT3DMZ-11-COMM

og

show ip route vrf CAT3DMZ-51-TPS-INT-SERVER

De vil vise os den anden halvdel af modellen: hvordan en CAT3 firewall-zone faktisk fortsætter fra firewall → core → server-subnet.

Så bagefter har vi begge retninger dækket:

CAT2 destination:
CAT3-FW → BGP → CAT2DMZ


CAT3 server destination:
CAT3-FW → linknet → CAT3-CORE VRF → server subnet

Det er meget værdifuldt til regressionstests senere.
